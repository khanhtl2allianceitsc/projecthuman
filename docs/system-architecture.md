# ProjectHuman — System Architecture

## 🏗️ System Overview

A distributed real-time dashboard with IP-based access control, stale-write detection, and full audit trails. PostgreSQL is the single source of truth; React Context manages client-side state.

```
┌─────────────────────────────────────────────────────────────────┐
│ CLIENTS (Browser)                                               │
│ ├─ React 19 + Context API                                      │
│ ├─ Optimistic updates                                          │
│ ├─ Stale detection (_updatedAt tracking)                       │
│ ├─ Dark/light theme                                            │
│ └─ Identity/session management (IP→member)                    │
└────┬─────────────────────────────────────────────────────────┬─┘
     │ HTTP/JSON (CORS enabled)                                │
┌────┴─────────────────────────────────────────────────────────┴─┐
│ API SERVER (Express.js :4000)                                  │
│ ├─ Node.js Cluster (8 workers, auto-scaled to CPU)            │
│ ├─ 29 RESTful routes (CRUD + identity + volunteer + admin)    │
│ ├─ Write queue (serialization)                                 │
│ ├─ Transaction control                                        │
│ ├─ IP whitelist validation                                    │
│ ├─ Stale check (409 Conflict)                                 │
│ ├─ Audit logging                                              │
│ └─ Volunteer Lead workflow coordination                       │
└────┬─────────────────────────────────────────────────────────┬─┘
     │ TCP:5432                                                  │
     │ (PostgreSQL Protocol, 40 connections: 5/worker × 8)      │
┌────┴─────────────────────────────────────────────────────────┴─┐
│ PostgreSQL (Database)                                           │
│ ├─ members table (name, role, man_month, is_admin, audit)     │
│ ├─ projects table (status, priority, budget, volunteer lead)  │
│ ├─ project_members junction                                   │
│ ├─ user_identities (IP→member session mapping)               │
│ ├─ lead_volunteers (applications: pending/approved/rejected)  │
│ ├─ meta (version tracking)                                    │
│ └─ write_log (audit trail + snapshots)                        │
└─────────────────────────────────────────────────────────────────┘
```

## 🗄️ Database Schema & Design

### Table: `members`
```sql
CREATE TABLE members (
  id VARCHAR(50) PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  role VARCHAR(100) DEFAULT '',
  color VARCHAR(20) DEFAULT '#6366f1',      -- Hex color for avatar background
  avatar VARCHAR(20) DEFAULT '',            -- Emoji or initials
  man_month INT DEFAULT 0,                  -- Man month value for salary tier
  is_admin BOOLEAN DEFAULT FALSE,           -- Admin flag
  created_by_ip VARCHAR(60),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_by_ip VARCHAR(60),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Design Notes:**
- `id`: UUID or nanoid generated by client
- `created_by_ip`, `created_at`: Set once on INSERT, never updated
- `updated_by_ip`, `updated_at`: Updated on every change
- `avatar`: Single emoji or 2-char initials (stored as string)

### Table: `projects`
```sql
CREATE TABLE projects (
  id VARCHAR(50) PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  description TEXT DEFAULT '',
  status VARCHAR(50) DEFAULT 'planning',    -- 'active', 'completed', 'paused', 'planning'
  priority VARCHAR(50) DEFAULT 'medium',    -- 'low', 'medium', 'high', 'critical'
  color VARCHAR(20) DEFAULT '#6366f1',      -- Hex color for card background
  start_date DATE,
  end_date DATE,
  progress INT DEFAULT 0,                   -- 0–100 (%)
  budget BIGINT DEFAULT 0,                  -- Currency in cents (or base units)
  spent BIGINT DEFAULT 0,
  tags TEXT[] DEFAULT '{}',                 -- PostgreSQL array: {"backend", "urgent"}
  need_lead BOOLEAN DEFAULT FALSE,          -- Project requires lead assignment
  volunteer_deadline DATE,                  -- Deadline for lead applications
  created_by_ip VARCHAR(60),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_by_ip VARCHAR(60),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Design Notes:**
- `tags`: PostgreSQL native array type, JSON-serializable
- `budget`, `spent`: Stored as BIGINT (multiply currency by 100 for cents)
- `start_date`, `end_date`: Can be NULL (unscheduled projects)
- Status & priority: Enum-like strings (no formal CHECK constraint)

### Table: `project_members` (Junction)
```sql
CREATE TABLE project_members (
  project_id VARCHAR(50) NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  member_id VARCHAR(50) NOT NULL REFERENCES members(id) ON DELETE CASCADE,
  project_role VARCHAR(100) DEFAULT '',     -- 'Lead', 'PM', 'Frontend Dev', etc.
  PRIMARY KEY (project_id, member_id)
);
```

**Design Notes:**
- Composite PK ensures one role per member per project
- Cascading deletes: removing project/member auto-cleans assignments
- `project_role`: Flexible string (no enum)

### Table: `meta`
```sql
CREATE TABLE meta (
  key VARCHAR(50) PRIMARY KEY,
  value TEXT,
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
-- Seed: ('updated_at', '1710950000', NOW())
```

**Design Notes:**
- Global version tracker
- `value` stores UNIX epoch seconds as string (e.g., "1710950000")
- Client converts to milliseconds: `serverTs = parseFloat(meta.value) * 1000`
- Used for stale-write detection

### Table: `write_log` (Audit Trail)
```sql
CREATE TABLE write_log (
  id SERIAL PRIMARY KEY,
  event VARCHAR(50),          -- 'READ', 'WRITE_OK', 'STALE_REJECTED', 'BLOCKED', etc.
  ip VARCHAR(60),             -- Source IP address
  detail TEXT,                -- Human-readable description
  snapshot JSONB,             -- Full data state before write (nullable)
  created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_write_log_created ON write_log (created_at DESC);
```

**Design Notes:**
- `event`: Fixed set of values logged by API
  - `READ`: Data fetch
  - `WRITE_OK`: Write succeeded
  - `WRITE_ERROR`: Write failed
  - `STALE_REJECTED`: 409 Conflict detected
  - `BLOCKED`: IP not whitelisted
  - `MANUAL_RESTORE`: Snapshot restore executed
  - `SERVER_START`: Server startup

- `snapshot`: JSONB of `{ members, projects, user_identities, lead_volunteers }` before write
- Indexed on `created_at` for fast recent-entry queries
- Last 30 snapshots retrievable, older ones kept for compliance

---

### Table: `user_identities` (Session Mapping)
```sql
CREATE TABLE user_identities (
  ip VARCHAR(60) PRIMARY KEY,     -- IP address (session key)
  member_id VARCHAR(50) FK,       -- Mapped member
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**Design Notes:**
- Stores IP→member mapping for identity/session system
- One member per IP; one IP can map to only one member at a time
- Updated on login, can be deleted on logout

---

### Table: `lead_volunteers` (Volunteer Applications)
```sql
CREATE TABLE lead_volunteers (
  id UUID PRIMARY KEY,
  project_id VARCHAR(50) NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  member_id VARCHAR(50) NOT NULL REFERENCES members(id) ON DELETE CASCADE,
  status VARCHAR(50) DEFAULT 'pending',     -- 'pending', 'approved', 'rejected'
  note TEXT,                                -- Application note from member
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(project_id, member_id)
);
```

**Design Notes:**
- Tracks member applications to lead projects
- Only one application per member per project (enforced by unique constraint)
- Approved status automatically rejects competing applications for same project
- Deleted when project or member is deleted (cascade)

## 🔐 Security Model

### IP Whitelist
- Config stored in `server/config.json`
- Format: `{ "allowedIPs": [...] }`
- Special value `"*"` = allow all IPs
- Checked on every POST request
- Used for edit permission on client (show/hide admin panel)

**Flow:**
```
Client IP → X-Forwarded-For (if proxied) → socket.remoteAddress
           → Strip IPv6 ::ffff: prefix
           → Compare against config.allowedIPs
           → Block (403) or Allow (proceed)
```

### Stale-Write Detection
Prevents last-write-wins conflicts in concurrent edits:

```
Time:    T0               T1               T2
Client A gets data (_updatedAt = 1000)
Client B gets data (_updatedAt = 1000)
                    A edits → POST (_updatedAt=1000, data=A')
                                 → Server version = 2000
                                 → Accept (1000 < 2000 but within 1s threshold)
                                 → Update meta to 2000
                                 ← 200 OK, _updatedAt=2000
                    B edits → POST (_updatedAt=1000, data=B')
                                 → Server version = 2000
                                 → REJECT: 1000 < 2000 - 1000
                                 ← 409 Conflict + current data
                         B sees alert "data updated"
                         B retries with fresh _updatedAt=2000
```

**Threshold**: 1000ms allows 1 second of clock skew and network latency

### Audit Trail
Every write captured:
- **Event**: Type of operation
- **IP**: Source address
- **Detail**: Human-readable summary
- **Snapshot**: Full data before write (JSONB)
- **Timestamp**: When it happened

Enables:
- Compliance audits (who changed what, when)
- Debugging (state reconstruction)
- Recovery (restore to any snapshot)

## 🔄 Data Flow

### Read Flow (GET /api/data)
```
Client browser
     ↓
GET /api/data
     ↓
Express handler
     ↓
readData(pool)
     ├─ SELECT FROM members
     ├─ SELECT FROM projects
     ├─ SELECT FROM project_members
     ├─ SELECT FROM meta (get _updatedAt)
     └─ Reshape into JSON
     ↓
appendLog('READ', ip)
     ↓
Response { members, projects, _updatedAt }
     ↓
Client state updated
```

### Write Flow (POST /api/data)
```
Client browser (after user edit)
     ↓
setData() [optimistic]
     ↓
persist(data, _updatedAt)
     ↓
POST /api/data with payload
     ↓
Express handler
     ├─ Extract IP
     ├─ Check whitelist (403 if not allowed)
     ├─ Check stale: clientTs < serverTs - 1000ms?
     │     YES → 409 + current data + alert user
     │     NO  → proceed
     └─ enqueue(writeData)
     ↓
writeData() in serialized queue
     ├─ Get DB client
     ├─ BEGIN transaction
     ├─ readData() for before-snapshot
     ├─ UPSERT members (new: insert, old: update)
     ├─ UPSERT projects
     ├─ DELETE/INSERT project_members
     ├─ UPDATE meta (new version timestamp)
     ├─ COMMIT
     └─ appendLog('WRITE_OK', ip, snapshot=before)
     ↓
Response { ok: true, _updatedAt }
     ↓
Client updates updatedAtRef
```

## ⚡ Performance Considerations

### Performance Considerations

### Write Queue (Node.js Cluster)
- All POST requests serialized via promise queue PER WORKER
- Each worker has 5 DB connections (40 total across 8 workers)
- Auto-restarts on crash (PM2-like behavior if using cluster mode)
- Prevents concurrent database writes per worker
- Ensures consistency: no write races at DB level
- Cost: slightly higher latency under high load

### Indexes
- `write_log(created_at DESC)`: Fast recent-log queries
- `members(id)`: PK index (automatic)
- `projects(id)`: PK index (automatic)
- `project_members(project_id, member_id)`: Composite PK
- `user_identities(ip)`: PK index for session lookups
- `lead_volunteers(project_id, member_id)`: Unique constraint

### Connection Pooling
- Pool size: 5 connections per worker (8 workers = 40 total)
- Idle timeout: 30s
- Connection timeout: 5s
- Suitable for <1000 concurrent requests/min
- Adjust `max` in `server/index.js` if scaling

### Query Optimization
- No N+1 queries (batched selects in readData)
- Avoid complex JOINs (manual join in code)
- Snapshots kept as JSONB (no parsing overhead until restore)

## 🚀 Deployment Architecture

### Development
```
npm run dev
├─ node server/index.js (Express on :4000, Node.js Cluster 8 workers)
└─ vite --host (dev server on :5173, accessible on LAN)
```

### Production
```
npm run build
├─ tsc -b (TypeScript compilation)
├─ vite build (creates dist/ with optimized JS/CSS)
└─ node server/index.js (API only, serves static from dist/)
```

### Scaling
- **Horizontal**: Load balance multiple API instances, shared PostgreSQL
- **Vertical**: Increase pool size, add DB replicas for reads
- **Caching**: Redis layer for /api/data (if stale data acceptable)
