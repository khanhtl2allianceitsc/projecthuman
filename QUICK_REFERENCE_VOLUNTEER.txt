DATABASE SCHEMA
================================================================================

Table: lead_volunteers

  id          | SERIAL PRIMARY KEY
  project_id  | FK to projects (CASCADE)
  member_id   | FK to members (CASCADE)
  status      | pending | approved | rejected (default: pending)
  note        | TEXT (application message)
  created_at  | TIMESTAMPTZ (default: NOW())
  updated_at  | TIMESTAMPTZ (default: NOW())
  UNIQUE(project_id, member_id)

Related Fields:
  • projects.need_lead (BOOLEAN)
  • projects.volunteer_deadline (TIMESTAMPTZ)
  • project_members.project_role (updated to 'Lead' on approval)

================================================================================
WORKFLOW
================================================================================

USER APPLIES:
  1. Views project with needLead=true and deadline not passed
  2. Clicks "Tôi muốn làm Lead" button
  3. Calls apply(projectId, memberId)
  4. Status: pending
  5. Can withdraw via cancel()

ADMIN APPROVES:
  1. Views pending applications in ProjectsNeedingLead component
  2. Clicks checkmark to approve
  3. Calls approve(volunteerId)
  4. Actions:
     • Sets status to 'approved'
     • Makes member 'Lead' in project_members
     • Demotes previous Lead to 'Member'
     • Rejects all other pending for same project
     • Atomic transaction (BEGIN/COMMIT/ROLLBACK)

ADMIN REJECTS:
  1. Clicks X button
  2. Calls reject(volunteerId)
  3. Sets status to 'rejected'

================================================================================
KEY FACTS
================================================================================

✓ No random selection - explicit admin approval required
✓ One Lead per project - approving auto-demotes previous Lead
✓ Auto-reject pending - when one approved, others auto-rejected
✓ IP-based auth - uses user_identities table lookup, not sessions
✓ Soft deadline - optional volunteerDeadline, UI disables apply after
✓ Atomic approvals - uses BEGIN/COMMIT/ROLLBACK transactions
✓ Auto-polling - frontend refreshes every 10 seconds
✓ Audit logging - all actions logged to write_log table

================================================================================
AUDIT EVENTS
================================================================================

VOLUNTEER_APPLY    - User applies to be Lead
VOLUNTEER_CANCEL   - User withdraws application
VOLUNTEER_APPROVE  - Admin approves (logged with volunteerId, projectId, memberId)
VOLUNTEER_REJECT   - Admin rejects (logged with volunteerId)

All logged to: write_log table with IP, timestamp, detail, snapshot

AUTHORIZATION
================================================================================

Admin Check:
  SELECT is_admin FROM user_identities ui 
    JOIN members m ON m.id=ui.member_id 
    WHERE ui.ip=$1

On Startup:
  Sets is_admin=TRUE for member matching:
    • name ILIKE '%Trương Lê Khánh%'
    • name ILIKE '%Truong Le Khanh%'
